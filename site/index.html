deterministic workflow evaluation

Most evaluation tools check states.
MITER checks the transition.

Workflows are sequences of connected segments, and work fails at the join — an entity crossing into a new lane must meet the receiving lane’s conditions, inside a tolerance and a time budget. MITER makes that constraint checkable instead of metaphorical: a deterministic DSL with a natural-language compiler that turns plain English into executable evaluation specs.

Verdicts must be reproducible or they are not verdicts. Same spec + same data → byte-identical output, every run. No random, no sampling, no I/O in evaluation. Across the whole grammar: six releases, ninety-one tests, still fully deterministic.

§ 01 — the problem

Evaluation today fails in three quiet ways.

None of them are loud failures. Each one looks like a working process until the handoff breaks.

  1. State-checks miss the handoff. Both ends of a connection can read within spec and the link still breaks. The check that matters is the moment of crossing — and most tools never look there.
  2. Rubrics are prose. Acceptance criteria live in documents and drift from the code that enforces them. A spec should be versionable, diffable, and executable — not a paragraph on a wiki.
  3. Verdicts aren’t reproducible. An LLM-as-judge outcome is an opinion with a timestamp. You can’t audit it, you can’t re-run it, and you can’t prove to a regulator that the same input always yields the same answer.
§ 02 — the primitives

Resolutions are cheap and transitions are steel.

Everything formalizes one idea: the gating constraint in a workflow is the transition, not the state. Three primitives cover the whole surface — conditions, edge cases, and the handoff itself.

CRITERION

A field against a bound — depot capacity under 95 %, driver hours under 14. Error or warn; error fails the row, warn flags it.

VARIATION

An edge case applied as a deterministic perturbation — what happens to the same route at peak volume. Same spec, stressed input.

INTERFACE

The transition itself: an entity entering a lane must match the lane’s conditions within tolerance and time. Joins pair rows across subjects for real handoffs.

Plus dataset-level criteria: aggregates (v0.2), categorical equality (v0.3), two-leg joins (v0.4), and windowed rules (v0.5) — all in the same deterministic core.

# route_feasibility.mtr — real example from the repo
EVALUATION route
SUBJECT route
INPUTS stops depot_capacity driver_hours

CRITERION depot_within_capacity
    FIELD depot_capacity <= 0.95
    SEVERITY error

VARIATION peak_volume
    ADJUST depot_capacity SCALE 1.2
    NOTE what happens when volume spikes

INTERFACE merge_onto_expressway
    FROM collector TO expressway
    MATCH velocity TO lane_velocity
    TOLERANCE 0.15
    BUDGET 20m
    TIME merge_t

END
§ 03 — the demo

English in. Executable spec. Byte-identical verdicts.

This is not a mockup. This is the actual output of the current build — one phrase compiled, one dataset evaluated, the burst caught.

compiler

$ miter compile "no more than two missed deliveries in thirty days"

EVALUATION compiled_evaluation
SUBJECT subject
INPUTS missed_deliveries

CRITERION criterion_1
    FIELD missed_deliveries <= 0
    WITHIN 30d
    TIME t
    LIMIT 2
    SEVERITY warn
    NOTE window drafted from phrase

END
The compiler guesses encoding, never data — compiled specs are warn-severity drafts with a NOTE naming exactly what must be reviewed.

verdict — 60 route-days, misses clustered at days 10–12–13

  "windows":   [ { "id": "c1", "status": "FAIL",

run again?  byte-identical.  hash: 964024e8cdae1027
Three misses in a month is a normal week averaged out and a violation windowed. The rule reads “at most 2 per 30 days” — the burst fails the evaluation, deterministically.
No fabrication, anywhere. Missing data is N/A, never a guess. An unparsed phrase becomes a warn stub, never an invented threshold. The tool refuses to lie the way systems quietly do.
§ 04 — the envelope

What the DSL expresses — and what it refuses.

Five extensions, each shipped as its own version with its tests attached. The boundaries are empirical, not aspirational — probed against the running tool in the bounding analysis.

surfacesincewhat it handles
criteriav0.1numeric thresholds against fields, error/warn severity
aggregatesv0.2AVG / SUM / MIN / MAX / COUNT over the row set — batch QC
categoricalv0.3exact string equality — FIELD tag == "urgent"
two-leg joinsv0.4JOIN pairs rows across subjects — real dispatch handoffs
window clausesv0.5WITHIN 30d LIMIT 2 — bursts, not counts
compiler parityv0.6plain-English phrasings compile into all of the above
Explicitly refused — the boundary is the product:
  • LLM-as-judge inside a spec — a semantic criterion would break byte-determinism. The LLM stays outside, as a producer of fields, never the verdict authority.
  • Random sampling — any sample clause is a silent lie.
  • I/O during evaluation — external calls make verdicts unrepairable.
  • Stateful sequences — if evaluation needs state, the state belongs to the caller, given to MITER as input fields.
§ 05 — use it

Install and run.

$ pip install git+https://github.com/taretakt/miter
$ miter lint route_feasibility.mtr
$ miter run route_feasibility.mtr --data routes.json
$ miter compile "the route must respect depot capacity and driver hours"
Works offline, no services required. The interpreter, the compiler, and the full test suite are in one small repository — read the whole thing in an afternoon, audit it in an evening. MIT license, no telemetry, no accounts.
